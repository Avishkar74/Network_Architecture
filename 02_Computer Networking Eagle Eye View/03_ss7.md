# 3. SS7 (SIGNALING SYSTEM 7)

## What is SS7?

**SS7** is a signaling protocol from **1975** that handles call setup and SMS for telephone networks.

**Key fact:** There is a **second internet** running on SS7. You used it this morning (via SMS or a phone call) and you have never seen a packet from it.

**Critical innovation:** SS7 separated **signaling** from **voice**.

---

## In-Band vs Out-of-Band Signaling

### Before SS7: IN-BAND SIGNALING (Before 1975)

**Problem:** Voice and control signals on the same channel

```
One channel carries:
├─ Voice (what you say)
└─ Control signals
   ├─ 2600 Hz tone = "this trunk is idle"
   └─ MF (Multi-Frequency) tones = dialed digits
```

**Major security issue:** Anyone who can make the sound can make the decision
- Phone phreakers could generate 2600 Hz tones and manipulate the network
- No separation of concerns

### After SS7: OUT-OF-BAND SIGNALING (1975 onwards)

**Solution:** Separate networks for signaling and voice

```
┌─ Voice bearer (64 kbps DS0)
│  └─ The conversation (nothing else)
│
└─ Signaling network
   ├─ MTP (Message Transfer Part)
   ├─ SCCP (Signaling Connection Control Part)
   ├─ TCAP (Transaction Capabilities Application Part)
   ├─ MAP (Mobile Application Part)
   └─ ISUP (ISDN User Part)
```

**Benefits:**
- Signaling completely separate from voice
- Much greater security
- Can route signaling independently
- Packet-switched signaling network vs circuit-switched voice

**Modern analogy:** Same as **control plane** vs **data plane** in networking

---

## SS7 Protocol Stack

### The Five Layers (Simplified)

| Layer | Name | Protocol | Purpose |
|-------|------|----------|---------|
| L7 | Application | MAP, INAP, CAP, ISUP | Call setup, SMS, roaming |
| L5-L6 | Dialogue | TCAP | Transactions, ASN.1 encoding |
| L4 | Transport | SCCP | Subsystem routing, Global Title Translation |
| L3 | Network | MTP3 | Point code routing, load sharing |
| L2 | Link | MTP2 | Framing, sequencing, retransmission |
| L1 | Physical | MTP1 | 64 kbps DS0 on E1/T1 copper lines |

### Key Difference from TCP/IP

- **SS7:** A complete stack with specific responsibilities at each layer
- **TCP/IP:** TCP is only L4; TCP/IP stack is IP (L3) + TCP (L4) + applications (L7)

**Fair comparison:** Stack vs stack, not just one protocol vs one protocol

---

## SS7 vs TCP/IP Comparison

Both stacks solve the **same problems** at different layers, with different design decisions.

| Function | SS7 | TCP/IP |
|----------|-----|--------|
| **Sequencing** | FSN (7 bits), wraps at 128 | Sequence number (32 bits per byte) |
| **Acknowledgment** | BSN + BIB piggybacked on every SU | ACK number + SACK |
| **Retransmission** | BIB toggle; PCR on long/satellite links | RTO timers, fast retransmit on 3 dup-ACKs |
| **Flow Control** | SIB in LSSU (stop/go signal) | Sliding window in every segment |
| **Error Detection** | CRC-16 per signal unit | 16-bit ones-complement checksum |
| **Addressing** | Point Code (OPC/DPC) + SSN + Global Title | IP address + port number |
| **Connection Setup** | Connectionless; SCCP class 2/3 if needed | 3-way handshake (SYN, SYN-ACK, ACK) |
| **Congestion Control** | Hop-by-hop via MTP3 transfer-controlled | End-to-end (Reno, CUBIC, BBR) |
| **Scope of Reliability** | Per hop (between adjacent points) | End to end (across arbitrary hops) |
| **Max Payload** | 272 octets (SIF hard limit) | ~1460 B typical, 64 KB with window scaling |
| **Security** | None (trust by point code) | None natively; TLS layered above |

### Key Philosophical Difference

- **SS7:** Every hop is reliable (per-hop reliability)
- **TCP:** Only endpoints are reliable (end-to-end reliability)
- Both approaches were right for their networks

## Encapsulation in SS7

**"Seven layers of nesting to carry eleven bytes"**

When a GSM handset sends "Hello World!" via MO-ForwardSM:

```
L1 - MTP2 MSU (Message Signal Unit)
└─ Flag | BSN+BIB | FSN+FIB | LI | [SIO+SIF] | CRC-16 | Flag
   └─ SIF hard cap: 273 octets
   
     └─ L2 - MTP3
        └─ SIO 0x83 | DPC 2065 | OPC 2050 | SLS 5 | Payload
           └─ 129 octets

           └─ L3 - SCCP
              └─ UDT Msg 0x09 | class 1 | Called GT +447700900999 | Calling GT ...
                 └─ 99 octets

                 └─ L4 - TCAP
                    └─ BEGIN Tag 0x62 | OTID 0x00000001 | Dialogue AARQ
                       └─ 47 octets

                       └─ L5 - Invoke
                          └─ Tag 0xA1 | Invoke ID 1 | opCode 46 (mo-ForwardSM)
                             └─ 47 octets

                             └─ L6 - MAP (MO-ForwardSM-Arg)
                                └─ sm-RP-DA +447700900999 | sm-RP-OA +447700900456 | sm-RP-UI
                                   └─ 25 octets

                                   └─ L7 - SMS-SUBMIT TPDU
                                      └─ MTI | TP-MR | TP-DA | TP-PID | TP-DCS | TP-VP | TP-UDL 0x0C

                                         └─ L8 - TP-UD
                                            └─ C8 32 9B FD 06 5D DF 72 36 39 04
                                               └─ "Hello World!" (11 octets, 12 characters)
```

**Identical picture to Ethernet ⊃ IP ⊃ TCP ⊃ HTTP**

Different names, same onion. The payload just caps at 272 octets instead of 1460 B.

## SMS: The 140-Byte Limit

### Why Exactly 140 Bytes?

**Three independent length limits, stacked. The smallest one wins:**

```
272 octets
└─ SIF (MTP2 hard ceiling)
   └─ Physical limit of a single Message Signal Unit

   ~200 octets
   └─ sm-RP-UI (MAP's field)
      └─ What MAP is willing to carry as opaque user data

      140 octets
      └─ TP-UD (SMS payload field)
         └─ Chosen so the whole MAP operation always fits in one MSU
            └─ One SMS = one signaling packet, no fragmentation needed
```

### Why No Segmentation?

**"One SMS is always exactly one signaling packet"**

- No fragmentation
- No reassembly
- No held state
- Stateless = runs on 1980s hardware
- Still works when data network is down

This constraint was **driven by hardware limitations of 1980s signaling equipment**.

---

## GSM-7 Encoding: 160 Characters in 140 Bytes

### The Math

```
140 octets (TP-UD field)
× 8 bits per octet
= 1120 bits available

÷ 7 bits per character (GSM 7-bit alphabet)
= 160 characters
```

### Why 7 Bits?

ASCII uses 8 bits per character, which wastes a bit (ASCII is only 7 bits really).

GSM-7 is a 7-bit alphabet containing:
- All uppercase and lowercase letters
- All digits 0-9
- Common punctuation
- Some extended characters

### The Packing Trick

Characters are packed as septets (7-bit groups) into a continuous bit stream, then re-sliced into octets:

```
Character 1 (7 bits) │ Character 2 (7 bits) │ ... │ Character 12 (7 bits)
├─ After packing:
12 chars × 7 bits = 84 bits
84 bits → 11 octets (88 bits total, 4 bits zero-padded)
```

**Key point:** After the first character, character boundaries **stop lining up** with byte boundaries.

This is why the first character of `Hello World!` can look surprising in a packet capture. `H` has GSM-7 value `0x48`, but SMS does not store one character per byte. The first output octet combines the 7 bits of `H` with the first bit of the next septet (`e`), producing `0xC8` in the packed stream. `0xC8` is not a different encoding of just `H`; it contains bits belonging to two adjacent characters.

## When GSM-7 Breaks: UCS-2

### The Problem: Non-Latin Scripts and Emoji

When you use emoji or non-Latin characters:
- Cannot use GSM-7 (its 7-bit alphabet does not encode emoji)
- Must switch **TP-DCS to UCS-2** (2 bytes per character)

### The Impact

**Same 140-octet field, but now:**
```
140 octets ÷ 2 bytes per character = 70 characters
```

**One emoji can more than halve your message length!**

And it silently costs you a **second SMS** to send the rest:
- 160 characters GSM-7 = 1 SMS
- 1 emoji in UCS-2 = 1 SMS, only 70 characters available
- Message of 71 characters with 1 emoji = 2 SMSes

**Why this matters:** Phone plans count SMS by message, not by character

## SMS Flow: MO (Mobile-Originated) and MT (Mobile-Terminated)

### MO-ForwardSM: Phone A Sends to Phone B

```
Phone A (Handset)
├─ SMS-SUBMIT (TPDU, 140 octets max)
│
└─→ VMSC/VLR (A's serving switch)
    ├─ MAP mo-ForwardSM opCode 46
    │  └─ TCAP END — accepted, queued
    │
    └─→ SMSC (Store & Forward Center)
        └─ STORED. Delivery is now SMSC's problem.
        │
        └─→ Ask HLR (Subscriber Database)
        │   └─ MAP sendRoutingInfoForSM (MSISDN)
        │      └─ Returns: IMSI + serving MSC address
        │
        └─→ MSC B (B's serving switch)
            └─ MAP mt-ForwardSM (SMS-DELIVER)
            │  └─ SMS-DELIVER over the air
            │
            └─ Phone B
               └─ Delivery ack
            
            └─→ SMSC
                └─ MAP mt-ForwardSM result
                   └─ SMS-STATUS-REPORT (only if asked)
```

**Key phases:**
1. **Submission:** Phone A → VMSC → SMSC (immediate)
2. **Storage:** SMSC holds message in queue
3. **Routing:** SMSC queries HLR for B's location
4. **Delivery:** SMSC → MSC B → Phone B
5. **Report:** Optional status report back to Phone A

## Call Setup: ISUP (ISDN User Part)

### Four Messages Set Up a Call

**Important:** Signaling and voice are completely separate networks.

```
Phone A (Caller)                MSC A                 MSC B            Phone B (Callee)
├─ Off-hook + dialed digits
│
└─ IAM (Initial Address Message)
   └─ Called number, bearer request
      └─→ (travels through signaling network)
          └─→
              ├─ Ring signal sent to Phone B
              │
              └─ ACM (Address Complete Message)
                 ├─ Caller hears ringback
                 │
                 ├─→ (signaling message back)
                 │
                 └─ Phone B answers
                    │
                    ├─ ANM (Answer Message)
                    │  └─ Voice path cut through
                    │
                    └─→ (signaling message)
                    
                       ├─→ Voice bearer circuit (64 kbps, no SS7 involvement)
                       │   └─ Conversation flows here
                       │   └─ Signaling network completely IDLE during call
                       │
                       ├─ Phone A on-hook (hangs up)
                       │
                       └─ REL (Release)
                          │
                          └─→
                              ├─ RLC (Release Complete)
                              │  └─ Circuit freed
                              │
                              └─→
```

### Why Four Messages?

1. **IAM:** Caller → Originating switch (setup info)
2. **ACM:** Terminating switch → Caller (acknowledged, ringing)
3. **ANM:** Callee → Caller (answer, voice path ready)
4. **REL/RLC:** Teardown

**Key insight:** During the conversation, **signaling network is completely idle**. It only handles the setup and teardown.

## Modern VoIP: SIP (Session Initiation Protocol)

### Same Idea, HTTP-Shaped

SS7 is **circuit-switched telephony**. Modern **5G uses IP-based signaling:**

```
Alice (UA/Softphone)
├─ INVITE sip:bob@scaler.com
│  └─ SDP offer (codec, bitrate info)
│
└─→ Proxy/SBC (Session Border Controller)
    └─ INVITE forwarded
       │
       └─→ Bob's UA/Softphone
           ├─ 100 Trying
           │
           ├─ 180 Ringing
           │  └─→ (back to Alice)
           │
           ├─ Bob answers
           │
           └─ 200 OK
              └─ SDP answer (codec, bitrate)
                 │
                 └─→ Proxy
                     │
                     └─→ Alice
                         │
                         └─ ACK (end-to-end acknowledgment, bypassing proxy)
                         
                         ├─ RTP/SRTP media (UDP, direct peer-to-peer)
                         │  └─ Voice flows here
                         │  └─ Proxy is NOT involved
                         │
                         ├─ Alice hangs up
                         │
                         └─ BYE
                            │
                            └─→ Bob
                                │
                                └─ 200 OK
```

### Differences from SS7

| Aspect | SS7 | SIP |
|--------|-----|-----|
| Protocol | Proprietary, binary | Text (HTTP-like) |
| Status codes | IAM, ACM, ANM, REL | 100, 180, 200, 404, etc. |
| Media | Circuit-switched voice (64k DS0) | RTP/SRTP over UDP |
| Addressing | E.164 phone numbers, point codes | SIP URIs (sip:user@domain) |
| Control/Data split | SS7 network + PSTN voice | SIP signaling + RTP media |

**Signaling is still text; media is RTP over UDP. Control and data stay on separate paths.**

## SS7 Reliability vs TCP Reliability

### SS7: Per-Hop Reliability

**Every hop is reliable, between adjacent signaling points**

```
Point A → (reliable hop) → Point B → (reliable hop) → Point C

Each hop guarantees delivery to the next hop.
End-to-end reliability emerges from per-hop guarantees.
```

### TCP: End-to-End Reliability

**Only the endpoints are responsible for reliability**

```
Client → (unreliable network) → Server

TCP layer at client and server handle retransmission.
Middle hops don't care about loss.
```

### Why SS7 Chose Per-Hop

- Signaling network was **small and controlled** (telephone company equipment)
- **No internet-scale paths** with hundreds of hops
- **Critical reliability:** Every call setup must succeed
- **Simple** per-hop guarantees are easier to verify

### Why TCP Chose End-to-End

- **Large-scale internet** with unpredictable paths
- **Heterogeneous equipment** from different vendors
- **Per-hop reliability doesn't scale** (millions of devices)
- **Application-level reliability** is needed anyway (TCP retransmits, but apps still need timeouts)

**Both are correct for their context.**

## BBR: Beyond Packet Loss

### Traditional Congestion Control (Reno, CUBIC)

**Problem:** Uses packet loss as the signal for congestion

```
In-flight data over time (traditional TCP):

     ↗────────┐  ← Buffer fills until packets drop
    ↗         │
   ↗          ├─────────→ Drop detected, halve window
  ↗           │           ↘
              ↓            ↘──→ Slow start again
              
        Sawtooth pattern (repetitive)
```

**The bug:** On a link that drops packets for **non-congestion reasons** (wireless loss, cross-traffic), TCP crawls.

### BBR: Measure Actual Capacity

**Instead of waiting for loss, measure bottleneck bandwidth × RTT**

```
WHAT BBR MEASURES:
├─ Bottleneck bandwidth (max rate the path can carry)
└─ Round-trip propagation time (delay)

Send at: bandwidth × RTT = amount of data in flight

Keep the queue near empty, no packet loss needed.
```

**Results (Google):**
- Up to **2,000× throughput** on some benchmarks
- **Much lower latency**
- Works on lossy links (wireless, satellite)
- Works on long, fat pipes (intercontinental links)

**Cost:** More complex algorithm, requires time-based measurements
